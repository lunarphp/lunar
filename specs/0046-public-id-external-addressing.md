# 0046 — `public_id` for externally-addressable models

- Status: proposed
- Author: Glenn Jacobs
- Created: 2026-06-30
- TODO item: Add `public_id` (ULID) to externally-addressable models

## Problem

Every model is addressed solely by its auto-increment primary key (`bigIncrements id`). Nothing in the package exposes a stable, non-sequential external identifier. Before a storefront REST API, webhooks, a change feed, or third-party integrations are built (all on the roadmap), the identifier those integrations key off needs to exist and be stable — retrofitting one **after** adopters and integrations address records by `id` is a breaking change to every external contract at once.

Sequential integer keys are a poor external identifier on three counts:

- **They leak business data** — `orders/41` tells an observer the store has taken ~41 orders; `orders/9000` next month reveals volume.
- **They are guessable/enumerable** — any external URL or API path keyed by `id` invites trivial enumeration.
- **They are not portable** — a backfill, a merge, or a cross-environment sync cannot preserve integer keys, so any integration pinned to `id` breaks on data movement.

The codebase already anticipates this. `Models\Concerns\InvalidatesCache::cacheKey()` returns `$this->getKey()` with the comment: *"The seam through which the tag scheme can later move from the primary key to a stable `public_id`."* And `Order` already separates a human-facing `reference` (e.g. `00000001`, generated by `ReferenceGenerator`) from its key — but `reference` is display copy, sequential, and order-only; it is not a general external address.

This is **additive** (a new unique column + a generated value), so it carries no migration cost in the schema-reshaping sense. It is kept **pre-alpha** because it is foundational: external addressing must stabilise before anything is built against it.

## Proposal

Add a `public_id` column holding a **ULID** to the set of externally-addressable models, generated on create, unique per table, and exposed as the external address. The integer `id` stays the internal primary key and the foreign-key target for every relation; `public_id` is purely the outward-facing handle.

### Why ULID, not UUID or a prefixed id

- **Time-ordered** — ULIDs sort lexically by creation time, so they index well (no random-insert B-tree fragmentation that UUIDv4 causes) and a `public_id` ordering is a rough chronological ordering.
- **Compact and URL-safe** — 26 Crockford-base32 chars, case-insensitive, no hyphens; cleaner in a URL than a 36-char UUID.
- **Native ULID generation in Laravel** — `Illuminate\Support\Str::ulid()`. We deliberately do **not** use the framework's `HasUlids` trait: that trait is designed for models whose **primary key** is a ULID (it overrides `uniqueIds()`, the key type, and route binding). Here the primary key stays the integer `id`; `public_id` is a secondary unique column, so a small bespoke concern is the right fit.
- **Unopinionated** — a plain ULID with **no type prefix** (no `prod_…`/`order_…`). Prefixing is a consumer/API-layer presentation choice; core ships the raw stable id and stays out of naming conventions — consistent with Lunar's unopinionated boundary (core ships facts about its data, not consumer presentation conventions).

### The `HasPublicId` concern

A new trait in `Models\Concerns\HasPublicId` (the established place for shared model behaviour — `HasChannels`, `HasMedia`, …):

```php
use Illuminate\Database\Eloquent\Model;
use Illuminate\Support\Str;
use Lunar\Core\Models\Builders\Builder;

trait HasPublicId
{
    public static function bootHasPublicId(): void
    {
        static::creating(function (Model $model) {
            if (empty($model->public_id)) {
                $model->public_id = (string) Str::ulid();
            }
        });
    }

    /**
     * @param  Builder<static>  $query
     * @return Builder<static>
     */
    public function scopeWherePublicId(Builder $query, string|array $publicId): Builder
    {
        return $query->whereIn('public_id', (array) $publicId);
    }
}
```

- Generation is **lazy and non-clobbering** — a value supplied explicitly (a sync importing an upstream id) is preserved; otherwise a ULID is minted. This keeps the door open for the change-feed/sync work to carry ids across environments.
- A `wherePublicId()` scope is the canonical lookup seam; the storefront API and integrations resolve by it. Its query parameter is the package's custom `Models\Builders\Builder` (the one `Base::newEloquentBuilder` returns), so the scope is phpstan-clean.
- The trait carries **no route-binding override** — route binding stays on `id` (see below).

### Which models get one

**Tier 1 — externally-addressable:**

| Model | Table |
|---|---|
| `Product` | `products` |
| `ProductVariant` | `product_variants` |
| `Order` | `orders` |
| `Customer` | `customers` |
| `Collection` | `collections` |
| `Brand` | `brands` |

These are the entities an API, webhook, or integration references by identity. `Order` keeps `reference` (human display) **and** gains `public_id` (machine address) — they are different concerns: `reference` is the sequential number a customer quotes; `public_id` is the opaque, enumeration-resistant handle an integration uses.

**Tier 2 — included now, for the imminent API surfaces:**

| Model | Table | Rationale |
|---|---|---|
| `Cart` | `carts` | the storefront API addresses carts over HTTP; an opaque cart handle avoids exposing the sequential key in cart URLs |
| `Discount` | `discounts` | externally referenceable once a discounts/promotions API exists ([[0047-split-promotions-from-discounts]]) |

If [[0047-split-promotions-from-discounts]] lands first, the campaign-level `Promotion` becomes the natural external-addressing target and inherits this column (the effect-level `Discount` is addressed through its promotion); whichever of the two specs lands second adjusts the table accordingly.

**Excluded** — lines, addresses, transactions, fulfilments, stock rows, prices, and all taxonomy/config models (`Currency`, `TaxClass`, `Region`, …). These are addressed **through their parent** (`orders/{public_id}/lines/…`) or are configuration referenced by handle/code, not identity. Adding `public_id` to them later is itself additive, so excluding them now costs nothing.

### Column shape

On each included table (baseline still open, so born on the `create_*_table` migration, not a later alter):

```php
$table->ulid('public_id')->unique()->after('id');   // NOT NULL
```

`NOT NULL` on the baseline: the `creating` hook always fills it on a fresh install, so a raw query-builder insert that skips it fails loudly rather than persisting a broken (null) external address. The nullability needed for the *upgrade* backfill window lives only in the upgrade migration (add nullable -> backfill -> tighten to `NOT NULL`), not the baseline.

### Route binding stays on `id`

`getRouteKeyName()` is **not** flipped globally. Filament and admin routes resolve models by `id` today, and switching the default route key would break every admin URL and any consumer route-model binding. Instead:

- Internal/admin binding stays `id` (default).
- External addressing resolves explicitly via `wherePublicId()` (the API layer's job).

A consumer that wants `public_id` route binding for their own storefront routes opts in per-model with a standard `getRouteKeyName()` override — we document the recipe rather than imposing it.

### Search and cache seams

- **Search** — `getScoutKey()` stays `id` (changing the Scout key reshapes existing external indexes — breaking for adopters mid-flight). To make `public_id` a filterable/returnable search field, it is added to the **per-model indexers** that build the searchable payload (`ProductIndexer`, `OrderIndexer`, `CustomerIndexer`, `CollectionIndexer`, `BrandIndexer` each emit their own array starting `'id' => (string) $model->id`; each gains `'public_id' => (string) $model->public_id`). `ProductOption` is searchable but is not a `public_id` model, so it is skipped.
- **Cache** — `InvalidatesCache::cacheKey()` stays `id`. Moving the cache-tag vocabulary to `public_id` (the seam the comment anticipates) is a **follow-on**, not bundled here: it interacts with the tag scheme shipped in [[0044-storefront-cache-tagging]] and the invalidation events in [[0043-cache-invalidation-and-events]], and is worth its own change. This spec lays the column the seam will later read.

### Filament

Each Tier 1/2 resource surfaces `public_id` as a **read-only, copyable** field (infolist entry + an optionally-toggled, copyable table column), so an operator can grab the external id for support/debugging. It is never editable.

## Alternatives considered

- **UUIDv4.** Universally understood, but random ordering fragments the unique index on insert and gives no chronological signal. ULID wins on index locality and sortability. Rejected.
- **UUIDv7.** Also time-ordered and a reasonable choice; ULID is chosen for the existing Laravel `Str::ulid()` ergonomics and the shorter Crockford-base32 string. A defensible alternative, not a meaningfully different outcome.
- **The framework `HasUlids` trait.** Targets models with a ULID *primary key* (overrides the key type and route binding). We keep the integer PK and add a secondary `public_id`, so the trait does not fit; a bespoke concern is cleaner. Rejected.
- **Reuse `Order::reference` as the external id (and add equivalents elsewhere).** `reference` is sequential (leaks volume), display-formatted, and order-specific. It is a customer-quotable number, not an enumeration-resistant machine address. They coexist. Rejected as the external id.
- **Flip the global route key to `public_id`.** Cleanest external URLs, but breaks all admin/Filament routing and any consumer binding on `id`, for no internal benefit. Rejected — keep `id` internal, expose `public_id` at the API seam.
- **Type-prefixed ids (`prod_01H…`).** Friendly in logs/URLs, but opinionated; presentation belongs to the API layer. Core ships the raw ULID. Rejected for core.
- **Do nothing / add per-model on demand.** The whole point is to stabilise the identifier **before** integrations bind to `id`; deferring means the eventual addition is a coordinated breaking change across every external contract. Rejected.

## Migration impact

- **Database** (baseline editable, v2 pre-release): a `ulid('public_id')->unique()` (NOT NULL) column born on each of the eight included `create_*_table` migrations (`products`, `product_variants`, `orders`, `customers`, `collections`, `brands`, `carts`, `discounts`).
- **Breaking changes to the public contract surface:** none for existing consumers — purely additive. New surface: `Models\Concerns\HasPublicId`, the `public_id` attribute + `wherePublicId()` scope on the included models, `public_id` in the relevant search indexers.
- **Upgrade path for v1.x consumers:** the upgrade package, for each included table, adds the column **nullable**, **backfills** a ULID into every existing row in batches (seeding each ULID's timestamp from the row's `created_at` via `Str::ulid($createdAt)`, so migrated `public_id`s sort by record creation time exactly as freshly-minted ones do), then **tightens the column to `NOT NULL`** and relies on the unique index. One-way (the upgrade data migrations are not reversible; restore from backup to undo). No Rector rule (no code-surface rename).
- **Translation / locale impact:** one new Filament label per resource (`public_id` field), English-first then mirrored across the other 15 locales.
- **Filament / admin impact:** read-only copyable `public_id` infolist entry (and optional table column) on the Tier 1/2 resources. No editing, no validation.

## Resolved decisions

- **Scope: Tier 1 + Tier 2 (eight tables).** The six catalog/commerce entities plus `Cart` and `Discount`, since the storefront-API and promotions work both address these over HTTP and the column is additive.
- **Column is `NOT NULL` on the baseline.** The `creating` hook always fills it on fresh installs, so a null external address can never persist; the nullable window exists only inside the upgrade backfill (nullable -> backfill -> tighten).
- **Backfill seeds the ULID timestamp from `created_at`.** Migrated `public_id`s sort chronologically like fresh ones, rather than by backfill iteration order.
- **Cache-key cutover is deferred.** `cacheKey()` stays `id`; moving the tag vocabulary to `public_id` is a separate change touching the 0043 events and the 0044 tag scheme. This spec only lays the column.
- **`HasUlids` is not used; route binding stays on `id`.** A bespoke `HasPublicId` concern adds a secondary unique column without disturbing the integer PK or route resolution.
