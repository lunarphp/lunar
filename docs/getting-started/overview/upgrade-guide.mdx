This page covers the tooling and steps for moving a Lunar v1.x application to v2.x.

## Overview

Lunar v2 is a wholesale breaking release. The core package moves to the `Lunar\Core\…` namespace, the admin panel splits into a `lunarphp/filament` bridge package, migrations are flattened into a single v2 baseline, and a long list of renamed columns, renamed classes, and reshaped data (pricing, selling policy, order status, regions, fulfilment) ship alongside it. See [What's new in Lunar v2](/getting-started/overview/introduction) for the full picture of what changed and why.

A dedicated package, [`lunarphp/upgrade`](https://github.com/lunarphp/lunar), automates as much of the v1 to v2 transition as possible:

- **Rector rules** rewrite class references, renamed methods, renamed properties, and money-attribute access patterns across application code.
- **Data migrations** transform the existing v1 database in place (column renames, enum reconciliation, backfilling new v2 concepts such as regions and fulfilments) rather than requiring a fresh install.
- **A guided CLI**, `php artisan lunar:upgrade`, runs the composer, config, data-migration, and migrations-ledger steps in order, with a dry run mode and a manual-actions report at the end.

`lunarphp/upgrade` is a dev dependency of the application being upgraded. It is not a runtime dependency of Lunar v2 itself, and it is not published as part of a fresh v2 install.

<Warning>
The upgrade package's data migrations are **one-way**. They have no `down()` method, so there is no automated rollback. Take a full database backup before running `php artisan lunar:upgrade`, and treat "restore from backup" as the only way back if something goes wrong partway through.
</Warning>

## Before upgrading

- Back up the database. This is the only recovery path if the upgrade needs to be undone.
- Commit or stash any uncommitted application changes.
- Make sure the application is fully up to date on the latest Lunar v1.x release and all its migrations have run. The upgrade command refuses to proceed otherwise.
- Run the upgrade against a staging copy of the database first, given the size of the breaking surface between v1 and v2.

<Info>
Coming from GetCandy (pre-v1.x)? The `lunar:migrate:getcandy` command that handled that transition exists only on Lunar v1.x and has been removed in v2. Reach v1.x first, run that command there, then continue with this guide.
</Info>

## Requirements

Lunar v2 raises the minimum platform requirements:

- PHP 8.4 or later.
- Laravel 12 or 13.
- Filament v5, if using the Filament-based admin panel (`lunarphp/filament` / `lunarphp/admin`).

Upgrade the application's PHP and Laravel versions before starting the Lunar upgrade if it is not already on these versions.

## Step-by-step

### 1. Require the upgrade package

```sh
composer require lunarphp/upgrade --dev
```

### 2. Run the upgrade command

```sh
php artisan lunar:upgrade
```

The command runs five steps in order, each tied to the spec that introduced it:

1. **`composer-require-rewrite`** — rewrites the application's `composer.json`, swapping `lunarphp/lunar` for `lunarphp/admin` in `require` / `require-dev`, and adding an explicit `lunarphp/core` requirement if it was previously only pulled in transitively. Run `composer update` afterwards to refresh the lockfile.
2. **`rector`** — reports how many class references the bundled Rector rules would rewrite across the configured paths.
3. **`step-list-config`** — reads the published `config/lunar/cart.php`, `pricing.php` and `orders.php` and reports any step-list keys they still define (see [Step lists move from config to code](#step-lists-move-from-config-to-code)). It does not edit the files.
4. **`data-migrations`** — runs the package's data migrations against the existing v1 schema: class-string rewrites, column renames, enum value reconciliation, and backfilling new v2 concepts (regions, fulfilments, stock, `public_id`).
5. **`ledger-rewrite`** — rewrites the application's `migrations` table so v1 Lunar migration rows are removed and the v2 flat baseline is recorded as already run, so future v2.x migrations layer on cleanly.

Useful options:

```sh
php artisan lunar:upgrade --dry-run              # print what each step would do, write nothing
php artisan lunar:upgrade --only=data-migrations  # run a single step by name
php artisan lunar:upgrade --skip=rector           # skip a step by name
php artisan lunar:upgrade --paths=app --paths=src # override the code paths Rector considers
php artisan lunar:upgrade --connection=upgrade    # target a non-default database connection
```

The command aborts before making any changes if the configured connection has no v1.x migration rows (nothing to upgrade) or already has v2 baseline rows recorded (already upgraded).

<Info>
The `rector` step in `lunar:upgrade` currently reports the rewrite plan rather than invoking Rector directly. Run Rector against the application separately, using the rule set the upgrade package ships:

```sh
vendor/bin/rector process --config=vendor/lunarphp/upgrade/config/rector.php
```

This covers the class, method, property, and money-attribute rewrites described below. Run it before or after the `lunar:upgrade` data migrations — the two operate on code and data respectively and do not depend on each other's order.
</Info>

### 3. Review the manual-actions report

After the data migrations run, `lunar:upgrade` prints a report of what happened per step, followed by any manual actions that need attention. Currently this includes:

- **Pricing no longer reads the logged-in user.** Add the storefront context middleware described in [Bare price calls return store defaults](#bare-price-calls-return-store-defaults).
- **Cart line, cart and order modifiers now run.** Review any modifiers the application registers; see [Modifiers now run](#modifiers-now-run).
- **`CalculateLine` and `CalculateLineSubtotal` are removed.** Replace calls with `$cart->calculate()` and read the line totals.
- **Published step-list config keys**, from the `step-list-config` step. A key that matches the v1 defaults is listed as safe to delete. A customized list is printed with the equivalent `Steps::for(...)` calls to paste into a service provider.
- **`Lunar\DiscountTypes\AmountOff` has been split** into `Lunar\Core\DiscountTypes\PercentageOff` and `Lunar\Core\DiscountTypes\FixedAmountOff`. Stored discount records are converted automatically (based on their `data.fixed_value` flag), but source code referencing `AmountOff` needs to be updated by hand to whichever type it meant, since a rename rule cannot infer that. The discount's `data.fixed_values` key is renamed to `data.amounts`, and the `data.fixed_value` flag is removed.

### 4. Publish config and clear caches

```sh
php artisan vendor:publish --tag=lunar --force
php artisan optimize:clear
```

Review the application's `lunar.upgrade` config (published from `lunarphp/upgrade`) before running the data migrations if the store uses non-default order statuses — see [Order status mapping](#order-status-mapping) below.

## What Rector automates

The bundled Rector configuration (`vendor/lunarphp/upgrade/config/rector.php`) applies several categories of rewrite across `app/`, `config/`, and `database/` by default:

- **Namespace moves.** Every class shipped by `lunarphp/core` moves from `Lunar\…` to `Lunar\Core\…` (for example `Lunar\Models\Product` becomes `Lunar\Core\Models\Product`, `Lunar\Facades\CartSession` becomes `Lunar\Core\Facades\CartSession`). Filament support classes extracted into the new `lunarphp/filament` bridge package move from `Lunar\Admin\Support\…` to `Lunar\Filament\…`.
- **Renamed methods and properties**, including `ProductType::mappedAttributes()` → `attributeMapping()`, `Price::$compare_price` → `$list_price`, and `ProductVariant::$purchasable` → `$selling_policy` (class-scoped, so the unrelated `CartLine`/`OrderLine` `purchasable` morph relation and the `customer_group_product.purchasable` pivot boolean are left untouched).
- **Money-attribute access.** v1's per-attribute `PriceDataType` value object is gone; casts now return raw integers with formatting on the model. Rector rewrites `$order->total->value` to `$order->total`, `$order->total->formatted()` to `$order->format('total')`, and `$price->price->unitDecimal()` / `unitFormatted()` on the catalogue `Price` model to `$price->unitDecimal('price')` / `$price->unitFormat('price')`. The same rewrite applies to `OrderLine`: `$line->unit_price->unitDecimal()` / `unitFormatted()` becomes `$line->unitDecimal('unit_price')` / `$line->unitFormat('unit_price')`, which divide by the line's own `unit_quantity` as v1 did. Unit calls on other money columns (line and order totals) are left for manual review.
- **`Model::modelClass()` calls** rewrite to `Model::class`, since model class substitution has been removed (see [Model extending](#model-extending-is-removed) below).
- **`Order::refund()` call sites** rewrite from three positional arguments to a `Lunar\Core\DataObjects\RefundRequest`: `$order->refund($transactionId, $amount, $notes)` becomes `$order->refund(new RefundRequest(transactionId: $transactionId, adjustment: $amount, notes: $notes))`.
- **Action call sites.** `SomeAction::run(...$args)` rewrites to `app(SomeContract::class)->execute(...$args)`, following the move to constructor-injected action classes bound to a contract.
- **Translated catalogue field access.** `$product->translateAttribute('name')` / `$product->attr('name')` rewrite to `$product->translate('name')` for `name` and `description`, now dedicated translatable columns instead of `attribute_data` entries.
- **`ShippingOption` pickup flag.** `$option->collect` and the `collect:` named argument rewrite to `$option->pickup` and `pickup:`.
- **`getThumbnailImage()` returns `?string`.** `HasThumbnailImage::getThumbnailImage()` now returns `null` when a record has no thumbnail, as `Product`, `ProductVariant`, and `Collection` do, instead of an empty string. Rector retypes a consumer's `getThumbnailImage(): string` to `?string` and replaces a `''` fallback in it with `null`. Code that passes the result into a `string` parameter should accept `null`.
- **Custom price formatter signatures.** A consumer's own `PriceFormatterInterface` implementation has its `$formatterStyle` parameter retyped from `string` to `int` on `formatted()`, `unitFormatted()`, and `formatValue()`, matching the `NumberFormatter::*` constants it receives.

## What the data migrations do

The package ships one data migration per v1 to v2 schema change, run in dependency order by the `data-migrations` step:

- **Class-string rewrite** — updates persisted class strings (discount conditions, purchasable morphs, and similar) from `Lunar\…` to `Lunar\Core\…`.
- **`compare_price` → `list_price`** — renames the column on `prices`.
- **Catalogue `name` / `description` columns** — adds dedicated translatable columns and migrates the equivalent `attribute_data` values onto them.
- **Attribute data keys to IDs** — converts the attribute system's handle-keyed storage to id-keyed storage.
- **Order line `requires_fulfilment` backfill.**
- **Stock backfill** — populates the new per-location `StockLevel` / `StockMovement` records from the v1 flat `stock` column.
- **Default region seed and backfill** — v1 has no region concept; this seeds a catch-all default `Region` from the v1 default channel, currency, and language, and backfills `region_id` on existing carts and orders.
- **Shipping line purchasable morph nulling** — shipping order lines no longer store a placeholder morph.
- **`purchasable` → `selling_policy`** — renames the column on `product_variants`, reconciles stored values onto the `SellingPolicy` enum's canonical set (correcting the `in_stock_or_backorder` typo some v1 test fixtures used), and maps any unrecognised value to `always` so the enum cast cannot throw after upgrade.
- **`public_id` backfill** — mints a ULID onto every addressable model.
- **Brand handle and status columns.**
- **Product type columns.**
- **Product variant `enabled` column.**
- **Collection and channel status columns.**
- **Soft-delete reconciliation** — v2 drops soft deletes from several models; this migration reconciles previously soft-deleted rows.
- **Order status and fulfilment backfill** — replaces the hand-set v1 `orders.status` headline with the derived `payment_status` / `fulfilment_status` rollups and the `closed_at` / `cancelled_at` archive columns, and materializes a whole-order `Fulfilment` record for each historically shipped order. See [Order status mapping](#order-status-mapping).
- **`AmountOff` discount type split** — converts stored `AmountOff` discount rows into `PercentageOff` or `FixedAmountOff` based on the discount's `data.fixed_value` flag (see the manual action above).
- **Product association `sort` column backfill.**
- **Cart `remember_token` column** — adds the nullable column used to [remember guest carts](/reference/carts#remembering-guest-carts). Existing carts get a token the next time they become a session's cart, so no backfill is needed.
- **Table-rate shipping `collection` driver** — renames the stored `shipping_methods.driver` key from `collection` to `pickup`, following the driver's rename to `Lunar\Shipping\Drivers\ShippingMethods\Pickup`. A no-op on stores without the table-rate-shipping package.
- **Order line `refunded_quantity` column** — adds the rollup of refunded quantity that line-item refunds increment. Existing lines default to `0`, since v1 recorded no line-item refunds.
- **Cart totals columns** — adds the persisted totals snapshot columns (`sub_total`, `total`, `revision`, `calculated_at`, and the rest) to `carts` and `cart_lines`. No backfill: every upgraded cart reads as not yet calculated and is filled in by its next `calculate()`.

### Order status mapping

v1's `orders.status` is a free-form string set by hand per store. v2 replaces it with two rollups derived from the order's transactions and fulfilments. The order-status data migration needs to know which of a store's v1 statuses map to which v2 concept, configured in `config/lunar/upgrade.php`:

```php
'orders' => [
    'fulfilled_statuses' => ['dispatched', 'complete'],
    'closed_statuses' => ['complete', 'cancelled', 'refunded'],
    'cancelled_statuses' => ['cancelled'],
],
```

The defaults cover the stock v1 statuses. Add any custom status strings the store uses to the appropriate list before running `php artisan lunar:upgrade`.

## Behavior changes

Three v2 changes alter what existing code does without a Rector rewrite, and each needs a decision in the application.

### Bare price calls return store defaults

In v1, `PricingManager::get()` read the authenticated user from the auth guard and priced against their customers' groups. In v2 the manager never reads the auth guard or the session. A bare `$variant->pricing()->get()` or `Pricing::for($variant)->get()` returns store-default prices (the default currency and customer group) for every visitor, unless the request has called `Lunar\Core\Facades\StorefrontSession::useAsDefaultContext()`. Nothing errors, so logged-in customers silently see retail prices.

To restore v1 behavior for bare storefront calls, add a middleware to the `web` group:

```php
<?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Lunar\Core\Facades\StorefrontSession;

class UseSessionStorefrontContext
{
    public function handle(Request $request, Closure $next): mixed
    {
        StorefrontSession::useAsDefaultContext();

        return $next($request);
    }
}
```

```php
// bootstrap/app.php
$middleware->web(append: [App\Http\Middleware\UseSessionStorefrontContext::class]);
```

It must run once per request, including Livewire update requests, which is why it belongs on the `web` group rather than in a service provider. With it in place, bare calls also follow the session's currency and region, which v1 ignored. See [Using the session as the default pricing context](/storefront-utils/storefront-session#using-the-session-as-the-default-pricing-context).

Related changes to the pricing manager:

- **No state carries between calls.** `get()` clears the purchasable, quantity and context after every call. Code that configured the manager once and then called `get()` in a loop must configure each call, for example `$variant->pricing($context)->get()`.
- **Explicit customer groups are no longer overridden** by the authenticated user's groups.
- **`user()` and `guest()` are deprecated.** Use `using($context)` or the new `customer(?Customer $customer)`. With the session as the default, a user with several customers is priced with the session customer's groups, not the merged groups of all of them.
- **`currency`, `customerGroups` and `user` are read-only.** Pricing pipelines can still read them, but writing to them is an error. Use the setters, or read `getContext()` from the contract.
- **`Lunar\Core\Contracts\PricingManager` gains** `getContext()`, `getPurchasable()`, `getQuantity()`, `customer()`, `guest()` and `get()`. A class implementing the contract directly must add them. `PricingManager`'s constructor takes `Lunar\Core\Contracts\DefaultStorefrontContext` and `Lunar\Core\Contracts\Actions\Storefront\ResolvesStorefrontContext` in place of the auth factory.
- **Jobs and commands** have no request, so a bare call there prices against store defaults. Pass a context, such as `$cart->context()`.

`Pricing::preventDefaultContext()` turns a bare call made without a context or a registered default into a `Lunar\Core\Exceptions\MissingStorefrontContextException`. Enable it outside production to find the calls that need a context.

### Modifiers now run

In v1, registered `CartLineModifier`, `CartModifier` and `OrderModifier` classes never ran during cart calculation or order creation. In v2 they do, so upgrading turns that code on. Review every modifier the application registers before deploying. Two details matter when reviewing one:

- `CartLineModifier::calculating()` runs before the line is priced, so a unit price set there is overwritten. Change prices in `subtotalled()`.
- A change to a line's subtotal in `subtotalled()` reaches discounts, tax and the cart total.

`Lunar\Core\Actions\Carts\CalculateLine`, `Lunar\Core\Actions\Carts\CalculateLineSubtotal` and their contracts (`CalculatesLine`, `CalculatesLineSubtotal`) are deleted. Cart calculation never used them. Call `$cart->calculate()` and read the line's totals instead. See [Extending Carts](/extending/carts#modifiers) for the hook points.

### Step lists move from config to code

The cart calculation, cart line pricing, price matching, order creation, cart validation and cart pruning lists are no longer read from config. These keys are removed:

- `lunar.cart.pipelines`
- `lunar.cart.validators`
- `lunar.cart.prune_tables.pipelines`
- `lunar.pricing.pipelines`
- `lunar.orders.pipelines`

v1 shipped `pipelines` and `validators` in its config, so most applications that published config still define some of them. While one is defined, the first read of any step list throws `Lunar\Core\Exceptions\RemovedStepConfigException`, naming the key. Artisan commands that read no list, including `lunar:upgrade`, still run.

The `step-list-config` step of `lunar:upgrade` reports each defined key. Delete keys that match the v1 defaults. For a customized list, delete the key and paste the printed `Steps` calls into a service provider:

```php
use Lunar\Core\Enums\StepList;
use Lunar\Core\Facades\Steps;

public function boot(): void
{
    Steps::for(StepList::OrderCreation)->append(App\Pipelines\Orders\CustomOrderPipeline::class);
}
```

Run `php artisan lunar:steps` afterwards to confirm what runs. See [Registering calculation steps](/extending/carts#registering-calculation-steps).

### Cart totals are persisted

v2 writes a cart's totals to the `carts` and `cart_lines` rows after each calculation, and `calculate()` serves them from the row for up to `lunar.cart.totals.ttl` seconds (default 300) while nothing on the cart has changed. Modifiers do not run when the snapshot is served. Three kinds of code need checking:

- Code that needs a guaranteed-fresh total, such as a payment amount check, calls `recalculate()`.
- Code that writes cart, line or address rows through the query builder calls `$cart->invalidateTotals()` afterwards.
- A modifier that sets a custom property on the cart or a line moves that data to the model's `meta`. A served snapshot restores the standard totals only.

See [Persisted totals](/reference/carts#persisted-totals).

## Manual checklist

Rector and the data migrations cover most of the mechanical work. Start with the three changes above: the storefront context middleware, registered modifiers, and published step-list config. The following also need a manual pass because they cannot be inferred automatically or depend on how the application used the feature.

<Warning>
**Model class substitution is removed.** v1 let an application swap a Lunar model for its own subclass via `ModelManifest::replace()` and have Lunar hand back instances of that subclass everywhere. v2 removes `HasModelExtending`, the `ModelManifest` substitution API, `Model::modelClass()`, and the `Models\Contracts\*` model interfaces entirely. Lunar models are now a single concrete class.

Rector rewrites `Model::modelClass()` calls to `Model::class`, but a subclass relying on substitution needs re-implementing through native Laravel mechanisms:

| Previously used substitution for… | Replace with |
|:--|:--|
| An added relationship | `Model::resolveRelationUsing('name', fn ($model) => …)` |
| An added method | A model macro via `Model::macro(...)` |
| An added column | Nothing extra — a migrated column is already a readable/writable attribute |
| A cast or accessor on an added column | `Model::addCasts(['column' => CastClass::class])` |
| A global query constraint | `Model::addGlobalScope(...)` |
| A lifecycle hook | `Model::observe(...)` or `Event::listen('eloquent.*: Class', ...)` |
| Overridden behaviour (not just data) | Bind the relevant action contract to a custom implementation in a service provider |

</Warning>

- **Untyped `->purchasable` accesses.** The `RenamePropertyRector` rule that renames `ProductVariant::$purchasable` to `$selling_policy` is class-scoped, so it only rewrites expressions Rector can type as `ProductVariant`. A fully untyped `$model->purchasable` is not rewritten and needs manual review — though most untyped occurrences are the unrelated `CartLine`/`OrderLine` purchasable morph or the `customer_group_product.purchasable` pivot boolean, which must not be renamed.
- **`AmountOff` discount type references.** As noted above, source code referencing `Lunar\DiscountTypes\AmountOff` needs a manual decision between `PercentageOff` and `FixedAmountOff`.
- **`ProductVariant::getTotalInventory()` for the `Always` selling policy.** v1 added the `backorder` allowance on top of `stock_available` for variants set to always sell. v2 returns the honest physical `stock_available` figure instead (the `Always` policy already short-circuits availability checks, so the old inflated number was never load-bearing for sell/no-sell decisions, but any code displaying or exporting the figure directly will see a lower number).
- **`Order::refund()` call sites Rector could not rewrite.** The refund rewrite only fires for exactly two or three positional, unnamed arguments on a receiver typed as `Order`. Calls already using named arguments, a different argument count, or an untyped receiver need a manual check against the new `RefundRequest` signature.
- **Removed config keys and Filament v3/v4 customizations.** Any published `config/lunar/*` files, Filament resources, or Blade views customized against v1 need reviewing against the v2 shape of the equivalent file — the upgrade package does not rewrite published assets. The `lunar.admin.order_count_statuses` key is removed with no replacement (the order navigation badge now counts open orders directly); override `OrderResource::getNavigationBadge()` for a different count.
- **Replaced extension hooks.** Two v1 admin extension hooks are removed rather than renamed, so Rector cannot rewrite them. A resource extension's `extendTable()` is replaced by a `configureTable(Table $table): Table` hook targeting the bridge table class (for example `Lunar\Filament\Tables\Currency\CurrencyTable`) instead of the resource. A list-page extension's `relationManagers()` is replaced by `getRelations()` on an extension targeting the resource itself. `extendTable()` still works when targeting a relation manager or relation page.
- **Subclasses of `CartSessionManager`.** `Lunar\Core\Managers\CartSessionManager`'s constructor takes an `Illuminate\Contracts\Cookie\QueueingFactory` and an `Illuminate\Http\Request` before the optional `$cart`. A subclass that calls `parent::__construct()` with positional arguments needs updating. Subclasses resolved from the container are unaffected.
- **Customer notifications now send by default.** v1 only sent the mailers listed under `lunar.orders.notifications` when an admin changed an order's status. v2 removes that config key and ships a default set of lifecycle emails (order confirmation, payment received, shipped, ready for pickup, provisioned, return received, cancelled, refund issued) that fire automatically on every install. Review the defaults against the store's existing emails: re-register a key to swap in the store's own notification class, or `OrderNotifications::forget()` any that should not send. A storefront that already sends its own order confirmation will now send two until it forgets `order-confirmation` or re-registers it. Any v1 mailer the store wants to keep becomes a Laravel `Notification` constructed with `(Order $order, ?string $message = null)` and is registered on the manifest from a service provider. A data import that creates placed orders should run inside `OrderNotifications::withoutSending()`. A notification meant for the refund action registers `on: ['refund-issued']`, not `on: ['refunded']` (which is the payment-status rollup). See [Notifications](/reference/notifications).
- **`lunar:migrate:getcandy`.** Removed in v2 with no replacement. Applications still on GetCandy-era data must run it on v1.x before upgrading further.
