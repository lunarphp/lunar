An order is a purchase created from a cart, tracked through payment and fulfilment until it is archived.

## Overview

An order is created from a [cart](/reference/carts) at checkout. It snapshots the cart's lines, addresses, and totals so the record stays accurate even if products, prices, or addresses change later. An order's lifecycle is read from two independently derived rollups, `payment_status` and `fulfilment_status`, plus an open/closed archive flag — there is no single headline "order status" column.

<Info>
All monetary values (such as `sub_total`, `total`, `tax_total`) are stored as integers in the currency's minor unit and cast through `Lunar\Core\Models\Concerns\FormatsPrices`, which exposes formatted/decimal accessors.
</Info>

Fulfilment (shipping, pickup, digital provisioning, tracking, carriers) is covered in full on the [Fulfilments](/reference/fulfilments) page. Sending emails to the customer is covered on the [Notifications](/reference/notifications) page. Capturing and refunding money through a payment provider is covered on the [Payments](/reference/payments) page — this page documents the order-side records those operations write to.

## Creating an order from a cart

An order is created from a cart via the `createOrder()` verb:

```php
use Lunar\Core\Models\Cart;

$cart = Cart::find(1);

$order = $cart->createOrder(
    allowMultipleOrders: false,
    orderIdToUpdate: null,
);
```

- `allowMultipleOrders` — a cart generally has one draft order associated with it. Pass `true` to allow multiple orders per cart (for example, a declined payment followed by a new checkout attempt with a different order).
- `orderIdToUpdate` — optionally pass the ID of an existing draft order (one with a null `placed_at`) belonging to the cart, to update it instead of creating a new one.

Before creating, the cart is validated against the `Lunar\Core\Enums\StepList::OrderCreateValidation` step list (defaulting to `Lunar\Core\Validation\Cart\ValidateCartForOrderCreation`), which throws a validation exception with a helpful message when the cart is not ready. Check readiness without throwing:

```php
$cart->canCreateOrder(); // bool
```

`createOrder()` delegates to `Lunar\Core\Contracts\Actions\Carts\CreatesOrder` (default `Lunar\Core\Actions\Carts\CreateOrder`), which fills the order's `cart_id` and `fingerprint`, then runs it through the `StepList::OrderCreation` step list. Core seeds it with:

```php
Lunar\Core\Pipelines\Order\Creation\FillOrderFromCart::class,
Lunar\Core\Pipelines\Order\Creation\CreateOrderLines::class,
Lunar\Core\Pipelines\Order\Creation\CreateOrderAddresses::class,
Lunar\Core\Pipelines\Order\Creation\CreateShippingLine::class,
Lunar\Core\Pipelines\Order\Creation\CleanUpOrderLines::class,
Lunar\Core\Pipelines\Order\Creation\MapDiscountBreakdown::class,
```

Each stage runs in order: `FillOrderFromCart` copies totals, currency, and customer data across and generates the reference; `CreateOrderLines` snapshots the cart's lines onto `OrderLine` rows; `CreateOrderAddresses` copies the cart's addresses; `CreateShippingLine` adds a `shipping` line when a shipping option was chosen; `CleanUpOrderLines` and `MapDiscountBreakdown` tidy up lines and rewrite the discount breakdown once discounts are marked as used. Registered `Lunar\Core\Modifiers\OrderModifier` classes run their `creating()` hook before the first step and their `created()` hook once the order is created, all inside the same database transaction. Add a custom step with `Lunar\Core\Facades\Steps::for(StepList::OrderCreation)` (see [Extending Orders](/extending/orders#order-creation-steps)), or replace `CreatesOrder`'s binding to change the flow entirely.

`payment_status` and `fulfilment_status` are not set explicitly during creation — they take the migration column defaults (`pending` and `unfulfilled`) until the first recompute runs (for example, when a transaction or fulfilment is recorded against the order).

### Order reference generation

The order reference is generated from `config/lunar/orders.php`:

```php
'reference_format' => [
    'prefix' => null,
    'padding_direction' => STR_PAD_LEFT,
    'padding_character' => '0',
    'length' => 8,
],

'reference_generator' => Lunar\Core\Orders\ReferenceGenerator::class,
```

The default generator pads the order's ID to `length` characters using `padding_character`/`padding_direction`, then prepends `prefix`. Set `reference_generator` to `null` to disable reference generation. A custom generator implements `Lunar\Core\Contracts\OrderReferenceGenerator`:

```php
namespace App\Orders;

use Lunar\Core\Contracts\OrderReferenceGenerator;
use Lunar\Core\Models\Order;

class CustomReferenceGenerator implements OrderReferenceGenerator
{
    public function generate(Order $order): string
    {
        return 'ORD-'.$order->id;
    }
}
```

## Order lifecycle

An order's lifecycle is read from three independent signals rather than one status column: whether it is a draft or placed (`placed_at`), its two derived rollups (`payment_status`, `fulfilment_status`), and whether it has been archived (`closed_at`) or cancelled (`cancelled_at`).

<Warning>
`payment_status` and `fulfilment_status` are **derived, unguarded rollups**, not a hand-driven state machine — there is no fixed transition graph and nothing to call `transitionTo()` on. They are recomputed automatically from the transaction ledger and the order's fulfilments whenever either changes, and any value can follow any other as the underlying records change.
</Warning>

### Payment status

`payment_status` is cast to a `Lunar\Core\States\Order\Payment\PaymentStatus` instance, rolled up from the order's `transactions`:

| State | `$name` | Meaning |
|:------|:--------|:--------|
| `Pending` | `pending` | No transactions recorded |
| `Voided` | `voided` | Transactions exist but none succeeded |
| `Authorized` | `authorized` | A successful payment intent exists, nothing captured yet |
| `PartiallyPaid` | `partially-paid` | Some, but not all, of the order total has been captured |
| `Paid` | `paid` | The full order total has been captured (or the order total is zero) |
| `PartiallyRefunded` | `partially-refunded` | The order was paid in full and part of it has since been refunded |
| `Refunded` | `refunded` | Everything captured has been refunded |

### Payment terms

`payment_terms` records when the order is meant to be paid. It is cast to the `Lunar\Core\Enums\PaymentTerms` enum:

| Case | Value | Description |
|:-|:-|:-|
| `Checkout` | `checkout` | Paid at checkout. The default |
| `OnAccount` | `on-account` | Invoiced and paid later |
| `OnPickup` | `on-pickup` | Paid in store when the customer collects |
| `OnDelivery` | `on-delivery` | Paid to the courier when the order is delivered (cash on delivery) |

An order placed on account, or for payment on pickup or on delivery, has no transactions, so its payment status is `Pending`, the same as an order whose card payment failed. The terms tell the two apart. Terms never change `payment_status`. Once money is recorded, the status moves on as usual (`PartiallyPaid`, `Paid`), and the order reads like any other.

```php
$order->payment_terms;              // PaymentTerms::OnAccount
$order->isAwaitingPaymentByTerms(); // true while the terms are not Checkout and the status is Pending
$order->paymentStatusLabel();       // "On account" while awaiting payment, otherwise the status label
```

The terms come from the cart, through [`$cart->setPaymentTerms()`](/reference/carts#payment-terms), or from the payment type, through a `terms` key in its config (see [Payments](/reference/payments#payment-terms)). The payment type wins.

A zero-total order is never `Pending`, because the payment status settles it as `Paid`. Its terms are stored as given, and `isAwaitingPaymentByTerms()` returns `false`. If the order is edited and its total rises, the status leaves `Paid` and the stored terms apply again.

### Fulfilment status

`fulfilment_status` is cast to a `Lunar\Core\States\Order\Fulfilment\FulfilmentStatus` instance, rolled up from the order's fulfillable lines and its `fulfilments` (see [Fulfilments](/reference/fulfilments) for the per-fulfilment lifecycle):

| State | `$name` | Meaning |
|:------|:--------|:--------|
| `Unfulfilled` | `unfulfilled` | None of the fulfillable quantity has been dispatched |
| `PartiallyFulfilled` | `partially-fulfilled` | Some, but not all, of the fulfillable quantity has been dispatched |
| `Fulfilled` | `fulfilled` | All fulfillable quantity has been dispatched (an order with nothing to fulfil resolves here immediately) |
| `PartiallyReturned` | `partially-returned` | Some dispatched quantity has been returned |
| `Returned` | `returned` | All dispatched quantity has been returned |

Both rollups recompute automatically whenever a `Transaction` or a `Fulfilment`/`FulfilmentLine` changes, dispatching `Lunar\Core\Events\Orders\OrderPaymentStatusUpdated` / `OrderFulfilmentStatusUpdated` when the value actually changes.

### Open and closed orders

Independently of payment and fulfilment, an order is either open (in the active work queue) or closed (archived):

```php
$order->close();   // Lunar\Core\Contracts\Actions\Orders\ClosesOrder
$order->reopen();  // Lunar\Core\Contracts\Actions\Orders\ReopensOrder
```

Both are idempotent — closing a closed order, or reopening an open one, is a no-op. A cancelled order cannot be reopened.

<Tip>
An order can be closed automatically the moment it becomes fully paid (`Paid`) and fully fulfilled (`Fulfilled`). It is off by default — bind a custom `Lunar\Core\Contracts\OrderSettings` implementation and return `true` from `autoClosesSettledOrders()` to opt in:

```php
use Lunar\Core\Contracts\OrderSettings;
use Lunar\Core\Models\Order;

class AutoCloseOrderSettings implements OrderSettings
{
    public function autoClosesSettledOrders(Order $order): bool
    {
        return true;
    }
}
```

Bind it in a service provider: `$this->app->bind(OrderSettings::class, AutoCloseOrderSettings::class);`. Auto-close never reopens an order that later regresses (a return or a partial refund) — that stays a deliberate `reopen()`.
</Tip>

### Cancelling an order

```php
$order->cancel(
    reason: 'customer',
    note: 'Customer changed their mind',
    notify: true,
);
```

Cancellation is one-way and covers status only — it does not issue a refund or restock inventory. An order can be cancelled as long as it is not already cancelled and nothing on it has shipped or returned. Cancelling voids the order's un-shipped fulfilments, stamps `cancelled_at`/`cancel_reason`/`cancel_note`, and also closes the order.

Reasons come from the `CancelReasons` manifest rather than config, so they can be adjusted per application:

```php
use Lunar\Core\Facades\CancelReasons;

CancelReasons::all();                          // array<string, string>
CancelReasons::add('warehouse-error', 'Warehouse error');
CancelReasons::forget('fraud');
```

### Component lines

A component line is an order line that belongs to another order line, linked by `parent_line_id`. The core ships the primitive; the [Bundles add-on](/addons/bundles) is what creates them today, one per part of a bundle, so that fulfilment, stock commitment, and returns see the parts of a kit while the customer's contract stays on one line.

A component line is a real order line. It has a `purchasable`, `type`, `requires_shipping`, `requires_fulfilment`, `identifier`, and `quantity`, so everything that walks order lines to fulfil, allocate, ship, return, or commit stock treats it like any other line. What it does not carry is money: `unit_price`, `sub_total`, `discount_total`, `tax_total`, and `total` are `0` and `tax_breakdown` is empty. The parent line holds the price, the tax, and the refundable amount; `refundableQuantity()` returns `0` for a component line, so refunds are recorded against the parent.

For reporting, a component line's `meta.allocated_total` holds its share of the parent's `total`, distributed across the parent's components in proportion to their unit prices with `Lunar\Core\Pricing\PriceCalculatorInterface::distribute()`. The shares sum exactly to the parent's total. It never feeds an order total.

```php
use Lunar\Core\Models\Order;

$order = Order::query()->findOrFail($id);

// Display: top-level lines with their components nested
$lines = $order->lines()->topLevel()->with('components.purchasable')->get();

foreach ($lines as $line) {
    $line->format('total');          // the money lives here

    foreach ($line->components as $component) {
        $component->quantity;                    // parts, not kits
        $component->meta['allocated_total'];     // reporting share of the parent's total
    }
}

$component->parent;          // the line it belongs to
$component->isComponent();   // true
```

Deleting a parent line cascades to its component lines. The order creation stages that match order lines to cart lines (`CreateOrderLines`, `CleanUpOrderLines`, `MapDiscountBreakdown`) only consider top-level lines, because a component line is never the image of a cart line.

<Warning>
`$order->lines`, `$order->productLines`, and the other line relations on `Order` include component lines. Code that iterates them for display or totals should use the `topLevel()` scope, or skip lines where `isComponent()` is `true`, or it will show zero-money rows and count parts as items.
</Warning>

<Info>
Shipping lines have no `purchasable` — a shipping option is a data transfer object rather than a model, so shipping lines are stored with no morph. Everything needed to display the line (`description`, `unit_price`, `total`, `meta`) is snapshotted onto the line itself. Guard for `null` when iterating `$order->lines`, or use `$order->productLines` to exclude shipping lines.
</Info>

## Transactions

### Capturing a payment

Capture an amount against a successful payment intent transaction:

```php
$capture = $order->capture(
    transactionId: $transaction->id,
    amount: 49.99, // major units, converted to the currency's minor unit internally
);

$capture->success; // bool
$capture->message; // string
```

`$order->capture()` delegates to `Lunar\Core\Contracts\Actions\Orders\CapturesOrder`, guards that the amount does not exceed the intent, and dispatches the driver's `capture()` — which creates the `capture` `Transaction`. Recording the capture triggers a `payment_status` recompute automatically.

### Recording a payment

Record a payment taken after checkout, such as a settled invoice or cash at the counter, with `recordPayment()`. The amount is in minor units.

```php
$transaction = $order->recordPayment(
    amount: 4550,
    reference: 'INV-1001',
    notes: 'Bank transfer',
);
```

`$order->recordPayment()` delegates to `Lunar\Core\Contracts\Actions\Orders\RecordsPayment` (default `Lunar\Core\Actions\Orders\RecordPayment`). It writes a successful `capture` transaction with the `offline` driver, and recording it triggers a `payment_status` recompute. Without a reference, it generates one. It throws `Lunar\Core\Exceptions\OrderActionException` when the amount is not positive or exceeds the outstanding balance.

```php
use Lunar\Core\Actions\Orders\RecordPayment;

RecordPayment::outstandingBalance($order); // the order total minus successful captures, in minor units
RecordPayment::canRun($order);             // an outstanding balance on an order that is not cancelled
```

A recorded payment refunds like any other capture: `Order::refund()` refunds it through the `offline` driver.

## Refunds

A refund targets a specific capture `Transaction` and can cover order lines, shipping, and a manual adjustment in one request:

```php
use Lunar\Core\DataObjects\RefundRequest;

$refund = $order->refund(new RefundRequest(
    transactionId: $transaction->id,
    lines: [
        ['order_line_id' => $line->id, 'quantity' => 1],
    ],
    shipping: 0,
    adjustment: 0,
    notes: 'Damaged on arrival',
    notify: true,
));

$refund->success;     // bool
$refund->message;     // ?string
$refund->transaction; // ?Lunar\Core\Models\Transaction — the refund transaction, when the driver records one
```

Each requested line is validated against its own `refundableQuantity()`, and the total requested amount is validated against the order's available-to-refund balance (captured minus already refunded). An amount-only refund — no line allocation — is expressed with an empty `lines` array and the whole amount on `adjustment`.

When the driver's refund succeeds and returns a `Transaction`, each line allocation is recorded as a `RefundLine` and the corresponding `OrderLine.refunded_quantity` is incremented:

## Notifying the customer

```php
$order->notifyCustomer(
    notification: 'order-update',
    message: 'Your order has been delayed by a day.',
    recipients: [], // defaults to the order's billing + shipping contacts
);
```

Lunar ships default emails for the order lifecycle (confirmation on placement, payment received, shipped, ready for pickup, provisioned, return received, cancelled, and refund issued), each overridable or removable from a service provider. See the [Notifications](/reference/notifications) reference for the full set, the notification manifest, mail routing, and how to customize the templates.

## Fulfilments

An order's shipped, picked-up, or digital fulfilment is tracked through `Fulfilment` records, created against the order's `fulfillableLines`:

```php
$fulfilment = $order->createFulfilment(
    lines: [$line->id => 1],
);
```

See the [Fulfilments](/reference/fulfilments) reference for the full fulfilment lifecycle, methods, carriers, and tracking.
