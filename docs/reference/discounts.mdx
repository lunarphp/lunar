Lunar applies discounts to a cart through a registry of discount type classes, each reading its own configuration from the discount's `data` column.

## Overview

A `Lunar\Core\Models\Discount` record describes *when* a discount is active, *who* it is available to, and *what* it targets. The `type` column names a class implementing `Lunar\Core\Contracts\DiscountType` that decides *how* the discount is applied to a cart. Lunar ships three types: percentage off, fixed amount off, and buy-x-get-y.


## Coupons: Coupon

A discount whose `redemption` is `coupon` applies only to a cart with one of its codes. Each code is a `Lunar\Core\Models\Coupon`, with its own usage count and limit. A discount can have one shared code or many codes, for example one per recipient of an email campaign. Redeeming a code needs no signed-in user and no customer on the cart: the code is the credential.

```php
Lunar\Core\Models\Coupon
```

|:------|:-----|:------------|
| `id` | `bigIncrements` | Primary key |
| `discount_id` | `foreignId` | |
| `code` | `string` | Unique across all discounts, cast through `Lunar\Core\Casts\CouponString`, which stores it uppercase |
| `uses` | `unsignedInteger` | How many placed orders have used the code |
| `max_uses` | `unsignedInteger` `nullable` | Maximum times the code can be used. No limit if `null` |
| `email` | `string` `nullable` | Who the code was issued to. Recorded for lookup and export, not checked when the code is redeemed |
| `batch` | `ulid` `nullable` | Groups the codes made by one generation run |
| `created_at` | `timestamp` | |

### Creating a coupon discount

```php
use Lunar\Core\Enums\DiscountRedemptionMethod;
use Lunar\Core\Models\Discount;

$discount = Discount::create([
    'name' => 'Spring sale',
    'handle' => 'spring_sale',
    'type' => \Lunar\Core\DiscountTypes\PercentageOff::class,
    'redemption' => DiscountRedemptionMethod::Coupon,
    'data' => ['percentage' => 10],
    'starts_at' => now(),
]);

$discount->coupons()->create(['code' => 'SPRING10']);

$discount->coupons()->create(['code' => 'VIP-ALEX', 'max_uses' => 1, 'email' => 'alex@example.com']);
```

`Lunar\Core\Contracts\Actions\Discounts\CreatesCoupon` and `Lunar\Core\Contracts\Actions\Discounts\DeletesCoupon` do the same through the container, and are what the admin panel calls. Deleting a code keeps its redemptions with a `null` `coupon_id`.

`redemption` is set explicitly rather than derived from whether a discount has codes, so deleting the last code of a coupon discount does not turn it into an automatic discount that applies to every cart.

### Generating codes

`Discount::generateCoupons()` creates a batch of codes on a discount and returns the batch ULID, which every code in the batch stores in its `batch` column. A `Lunar\Core\DataObjects\CouponBatch` describes the batch.

```php
use Lunar\Core\DataObjects\CouponBatch;

// 500 anonymous single-use codes.
$batchId = $discount->generateCoupons(CouponBatch::ofQuantity(500));

// One code per recipient, recorded in each code's email column.
$batchId = $discount->generateCoupons(
    CouponBatch::forEmails(['alex@example.com', 'sam@example.com'], prefix: 'SPRING-', length: 8),
);
```

| Method | Description |
|:-------|:------------|
| `CouponBatch::ofQuantity(int $quantity, ...)` | A number of codes with no `email` |
| `CouponBatch::forEmails(iterable $emails, ...)` | One code per distinct address. Addresses are trimmed and lowercased, as for [per-customer limits](#per-customer-limits), and blank entries are dropped |

Both take the same named options:

| Option | Default | Description |
|:-------|:--------|:------------|
| `length` | `10` | The number of generated characters after the prefix |
| `prefix` | `''` | Put before the generated characters, uppercased |
| `maxUses` | `1` | The `max_uses` of each code. `null` for no limit |

A batch with no codes, such as `ofQuantity(0)` or a list with no addresses, throws an `InvalidArgumentException`.

The batch ULID is set when the `CouponBatch` is created, and is available as `$batch->id`. Generating the same `CouponBatch` again completes the batch instead of adding codes to it, so a retried job does not make duplicates.

`generateCoupons()` delegates to `Lunar\Core\Contracts\Actions\Discounts\GeneratesCoupons`. The default action, `Lunar\Core\Actions\Discounts\GenerateCoupons`, inserts codes in chunks of 1,000 with `insertOrIgnore()` and keeps going until the batch is complete, so a code that collides with an existing one is replaced, not lost. If 10 chunks in a row insert nothing, the code space is nearly used up and it throws a `RuntimeException`; use a longer `length`. Codes are inserted in bulk, so no Eloquent model events fire for them.

#### Code generator

Each code comes from `Lunar\Core\Contracts\CouponCodeGenerator`, which has one method, `generate(CouponBatch $batch): string`. The default, `Lunar\Core\Generators\CouponCodeGenerator`, returns the prefix followed by `length` characters from an alphabet of uppercase letters and digits without the look-alike characters `0`, `O`, `1`, `I` and `L`. The generator does not need to return unique codes: the action replaces any that collide. Bind a different implementation in a service provider to change the format:

```php
use Lunar\Core\Contracts\CouponCodeGenerator;

$this->app->singleton(CouponCodeGenerator::class, MyCouponCodeGenerator::class);
```

#### Queueing large batches

`Lunar\Core\Jobs\GenerateCouponsJob` generates a batch on the queue. It carries the `CouponBatch`, so a retry completes the same batch.

```php
use Lunar\Core\DataObjects\CouponBatch;
use Lunar\Core\Jobs\GenerateCouponsJob;

$batch = CouponBatch::ofQuantity(50_000);

GenerateCouponsJob::dispatch($discount, $batch);

// $batch->id identifies the codes once the job has run.
```

The admin panel generates a batch during the request up to `lunar.discounts.coupons.queue_threshold` codes (default `5000`), and dispatches `GenerateCouponsJob` for a larger one. Code that calls `generateCoupons()` directly decides for itself. Measured locally against tables already holding 200,000 codes, 5,000 codes take about 0.1 to 0.2 seconds on SQLite, MySQL 8 and PostgreSQL, and 50,000 take 1 to 2.3 seconds. The time grows with the number of codes, not with the size of the table, and is spent almost entirely in the database inserts.

```php
// config/lunar/discounts.php
return [
    'coupons' => [
        'queue_threshold' => 5000,
    ],
];
```

#### Exporting codes

The admin panel exports a discount's codes, or one batch, as CSV with the columns `code`, `email`, `uses` and `redeemed_at` (the most recent redemption). In code, read a batch from the `coupons` relationship:

```php
use App\Mail\SpringCampaign;
use Illuminate\Support\Facades\Mail;
use Lunar\Core\Models\Coupon;

$discount->coupons()
    ->where('batch', $batchId)
    ->lazyById()
    ->each(fn (Coupon $coupon) => Mail::to($coupon->email)->queue(new SpringCampaign($coupon->code)));
```

`App\Mail\SpringCampaign` stands for the store's own mailable.

### Resolving a cart's code

`Lunar\Core\Models\Cart::coupon()` is a `BelongsTo` from the cart's `coupon_code` to `coupons.code`. Both columns are stored uppercase, so the relationship is a single indexed lookup and can be eager loaded. Everything that matches a cart's code reads it through `$cart->coupon`:

- `Discounts::getDiscounts()` loads automatic discounts, plus the discount `$cart->coupon` belongs to.
- `AbstractDiscountType::checkDiscountConditions()` passes a coupon discount only when `$cart->coupon` belongs to it and is usable.
- `Discounts::validateCoupon()` checks that the code exists, is usable, and belongs to an active, usable discount.

Changing `coupon_code` on a cart unloads its `coupon` relationship, so the next read resolves the new code.

When an order is created, `Lunar\Core\Pipelines\Order\Creation\MapDiscountBreakdown` adds `coupon_id` and `coupon_code` to each `discount_breakdown` entry that came from a coupon discount. The code is copied, so the order still shows it after the coupon is deleted.

## Usage: DiscountRedemption

Lunar counts a use of a discount when an order is placed, not when its draft order is created. A draft order is not a sale: a declined card or an abandoned checkout uses nothing, and a shopper who retries on the same cart, or on a new one, still gets the discount.

`Lunar\Core\Listeners\RecordDiscountRedemptions` handles `Lunar\Core\Events\Orders\OrderPlaced`. For each discount in the order's `discount_breakdown`, it records a `DiscountRedemption` and increments the discount's `uses`, and the coupon's `uses` for a coupon discount, each in a single database update. An order records each discount once, so the event firing again for the same order counts nothing.

### Per-customer limits

`max_uses_per_user` limits how many times one customer can use a discount. It applies to guests as well as signed-in customers. Lunar identifies the customer by user when there is one, and by email otherwise, and counts the redemptions that match either. A customer who has used a discount as a guest can't use it again by signing in, and a signed-in customer can't use it again by signing out, as long as the email is the same.

`Lunar\Core\Contracts\Actions\Discounts\ResolvesCustomerEmail` (default `Lunar\Core\Actions\Discounts\ResolveCustomerEmail`) decides which email identifies a cart's customer. It returns the first of:

1. the signed-in user's email;
2. the billing address `contact_email`;
3. the shipping address `contact_email`.

The billing address identifies the customer. The shipping address `contact_email` is used only when the billing address has none. The result is lower-cased and trimmed. To match emails more strictly, for example by ignoring `+tags`, bind your own implementation of the contract in a service provider.

`Lunar\Core\Contracts\Actions\Discounts\CountsCustomerRedemptions` (default `Lunar\Core\Actions\Discounts\CountCustomerRedemptions`) counts a discount's redemptions whose `user_id` is the cart's user or whose `email` is the resolved email. It returns `0` when the cart has neither.

The limit is enforced in three places:

- **Discount conditions.** Each cart calculation drops the discount once the customer's count reaches `max_uses_per_user`. A guest cart with no email yet keeps the discount, and drops it as soon as an email that has used it is added.
- **Coupon validation.** `Discounts::validateCoupon()` rejects a coupon the cart's customer has used up. See [Validating coupons](#validating-coupons).
- **Order creation.** `Lunar\Core\Validation\Cart\ValidateCustomerForDiscounts` runs in the `OrderCreateValidation` step list. It fails when a discount with `max_uses_per_user` is applied to the cart and the cart has neither a user nor an email, so `$cart->canCreateOrder()` returns `false` until the customer gives one.

Redemptions on cancelled and refunded orders keep counting, as `uses` does. Lunar does not give a use back when an order is cancelled.

### Going over a limit

Eligibility is checked on every cart calculation, so a discount at its `max_uses` no longer applies to new carts. Two carts priced with the last use can still both be paid for before either order is placed, and the same customer can pay for two carts at once. When a placement takes the discount's `uses` above its `max_uses`, the coupon's `uses` above its `max_uses`, or the customer's redemptions above `max_uses_per_user`, the listener keeps the order, because it has already been paid for, and reports it:

- It dispatches `Lunar\Core\Events\Discounts\DiscountLimitExceeded`, with public `order`, `discount`, `limit` and `coupon` properties. `limit` is a `Lunar\Core\Enums\DiscountLimit`: `DiscountLimit::MaxUses` for the discount-wide limit, `DiscountLimit::CouponMaxUses` for the coupon's own limit, or `DiscountLimit::MaxUsesPerUser` for the per-customer limit. `coupon` is the `Lunar\Core\Models\Coupon` the order used, or `null` for an automatic discount.
- It logs an activity on the order with the event `discount-limit-exceeded` and the properties `discount_id`, `discount` (the discount name), `coupon` (the code, or `null`), `limit` (`max_uses`, `coupon_max_uses` or `max_uses_per_user`), `uses` (the count that went over) and `max_uses` (the value of that limit).

A placement that goes over more than one limit dispatches the event once for each.

To hold such orders, or to alert someone, listen for the event:

```php
use Illuminate\Support\Facades\Event;
use Lunar\Core\Events\Discounts\DiscountLimitExceeded;

Event::listen(DiscountLimitExceeded::class, function (DiscountLimitExceeded $event) {
    // $event->order, $event->discount, $event->limit
});
```

## Built-in discount types

Every discount type extends `Lunar\Core\DiscountTypes\AbstractDiscountType` and implements `Lunar\Core\Contracts\DiscountType`:

```php
interface DiscountType
{
    public function getName(): string;
    public function apply(Cart $cart): Cart;
}
```

`AbstractDiscountType` provides shared behavior every type relies on:

- `checkDiscountConditions(Cart $cart): bool`: validates the discount against the cart before it applies anything, including, for a coupon discount, that `$cart->coupon` belongs to it and is usable, the cart customer against `customers()` (if restricted), a `data.min_prices` minimum spend for the cart's currency, `max_uses`, and `max_uses_per_user` (counted from the user's redemptions). Every shipped type calls this at the top of `apply()`.
- `addDiscountBreakdown(Cart $cart, DiscountBreakdown $breakdown)`: records how much this discount took off, and which lines it affected, on `$cart->discountBreakdown`.

`data.min_prices` is keyed by currency code and stored in minor units, and applies regardless of which type is used:

```php
'data' => [
    'min_prices' => [
        'USD' => 5000, // discount only applies once the cart reaches $50.00
    ],
],
```

### FixedAmountOff

```php
Lunar\Core\DiscountTypes\FixedAmountOff
```

Deducts a fixed, per-currency amount from the cart, distributed proportionally across eligible lines using the price calculator's largest-remainder allocation (so the total discount always exactly matches the configured amount).

```php
use Lunar\Core\Models\Discount;

Discount::create([
    'name' => '$5 Off',
    'handle' => '5_dollars_off',
    'type' => \Lunar\Core\DiscountTypes\FixedAmountOff::class,
    'data' => [
        'amounts' => [
            'USD' => 500, // $5.00 off, in minor units
            'EUR' => 450,
        ],
    ],
    'starts_at' => now(),
]);
```

| Data field | Type | Description |
|:-----------|:-----|:------------|
| `amounts` | `array<string, int>` | The amount to deduct per currency code, in minor units |

`PercentageOff` and `FixedAmountOff` both narrow the cart's eligible lines through `Lunar\Core\DiscountTypes\Concerns\TargetsCartLines`, which applies the discount's collection, brand, and `Discountable` limitations and exclusions before any amount is calculated.

<Info>
Prior to v2, this was a single `AmountOff` type switched by a `data.fixed_value` boolean. Every stored discount of that type is migrated by the upgrade package to either `PercentageOff` or `FixedAmountOff`, and `data.fixed_values` is renamed to `data.amounts`.
</Info>

### BuyXGetY

```php
Lunar\Core\DiscountTypes\BuyXGetY
```

"Buy X, get Y free" promotions. Condition products (the "buy" side) come from `discountableConditions`, reward products (the "get" side) from `discountableRewards`. Both accept products, product variants, or collections.

```php
use Lunar\Core\Models\Discount;

$discount = Discount::create([
    'name' => 'Buy 2 Get 1 Free',
    'handle' => 'buy_2_get_1',
    'type' => \Lunar\Core\DiscountTypes\BuyXGetY::class,
    'data' => [
        'min_qty' => 2,
        'reward_qty' => 1,
        'max_reward_qty' => 5,
        'automatically_add_rewards' => false,
    ],
    'starts_at' => now(),
]);

$discount->discountables()->create([
    'discountable_type' => Lunar\Core\Models\Product::morphName(),
    'discountable_id' => $product->id,
    'type' => 'condition',
]);

$discount->discountables()->create([
    'discountable_type' => Lunar\Core\Models\Product::morphName(),
    'discountable_id' => $rewardProduct->id,
    'type' => 'reward',
]);
```

| Data field | Type | Description |
|:-----------|:-----|:------------|
| `min_qty` | `int` | Minimum combined quantity of condition items required to trigger a reward |
| `reward_qty` | `int` | Reward items granted per qualifying group of `min_qty` condition items |
| `max_reward_qty` | `int` `nullable` | Caps the total reward quantity granted |
| `automatically_add_rewards` | `bool` | Whether qualifying reward items are added to the cart automatically |

Condition and reward matching also accepts collections: a `Discountable` entry with `discountable_type` set to a collection matches any cart line whose product belongs to that collection.

#### Automatically adding rewards

When `automatically_add_rewards` is `true` and a qualifying cart does not already contain enough reward items, `BuyXGetY` adds a cart line for the reward rather than requiring the customer to add it themselves:

- A reward candidate is chosen at random from the fulfillable `discountableRewards` (a collection reward picks a random fulfillable product from that collection).
- Only reward items that can currently be fulfilled at the required quantity are considered; an out-of-stock reward is skipped rather than raising an error.
- A reward quantity greater than one is added to a single cart line, not one line per unit.
- Added lines are tracked in the line's `meta.added_by_discount` for the discount's ID and quantity.

## The Discounts facade

`Lunar\Core\Facades\Discounts` resolves `Lunar\Core\Contracts\DiscountManager` (bound `scoped`, so a long-lived worker gets a fresh instance per request or job):

```php
use Lunar\Core\Facades\Discounts;
```

| Method | Returns | Description |
|:-------|:--------|:------------|
| `channel($channel)` | `DiscountManager` | Restrict discount lookups to the given channel(s) |
| `customerGroup($customerGroups)` | `DiscountManager` | Restrict discount lookups to the given customer group(s) |
| `getChannels()` | `Collection` | The currently set channels |
| `getCustomerGroups()` | `Collection` | The currently set customer groups |
| `getDiscounts(?Cart $cart = null)` | `Collection` | Active, usable discounts matching the current channel/customer group. When a cart is given, narrowed to its lines, and to automatic discounts plus the discount its coupon belongs to |
| `addType(string $classname)` | `DiscountManager` | Register a custom discount type |
| `getTypes()` | `Collection` | All registered discount type instances |
| `addApplied(CartDiscount $cartDiscount)` | `DiscountManager` | Record that a discount applied to a cart or cart line |
| `getApplied()` | `Collection` | The discounts recorded via `addApplied()` |
| `apply(Cart $cart)` | `Cart` | Runs every eligible discount's `apply()` against the cart, in `priority` order (highest first), stopping early if an applied discount has `stop = true` |
| `resetDiscounts()` | `DiscountManager` | Clears the memoized discount list, so the next `apply()`/`getDiscounts()` re-queries |
| `validateCoupon(string $coupon, ?Cart $cart = null)` | `bool` | Whether a coupon code is usable and belongs to an active, usable discount the cart's customer has not used up. The cart defaults to `CartSession::current()` |

`getDiscounts()` and `apply()` memoize the resolved discount list per cart state (cart ID, coupon code, customer, and line purchasables). Call `resetDiscounts()` after a change that should re-evaluate eligibility, for example after a coupon code is applied to the cart.

```php
Discounts::resetDiscounts();
```

### Registering a custom discount type

```php
use Lunar\Core\Facades\Discounts;
use App\DiscountTypes\FreeShippingOverThreshold;

Discounts::addType(FreeShippingOverThreshold::class);
```

Typically called from a service provider's `boot()` method. See [Extending Discounts](/extending/discounts) for how to build a custom discount type.

### Validating coupons

```php
use Lunar\Core\Facades\Discounts;

$isValid = Discounts::validateCoupon('20OFF');

$isValid = Discounts::validateCoupon('20OFF', $cart);
```

The default validator, `Lunar\Core\Validation\CouponValidator`, checks that the code is under its own `max_uses` and belongs to an active discount under its `max_uses` and, if the discount sets `max_uses_per_user`, that the cart's customer has not reached it, counted through `CountsCustomerRedemptions` (see [Per-customer limits](#per-customer-limits)). Without a cart argument it checks the cart from `CartSession::current()`. A guest whose cart has no email yet passes, because there is nobody to count against. Validate the coupon again once the customer gives an email; see [Re-validating a coupon once the email is known](/guides/cart#re-validating-a-coupon-once-the-email-is-known).

Bind a different implementation of `Lunar\Core\Contracts\CouponValidator` in your own service provider to customize this. The contract's signature is `validate(string $coupon, ?Cart $cart = null): bool`.

## How discounts apply in the cart pipeline

Eligibility is narrowed in two stages. First, `getDiscounts()` pre-filters candidate discounts at the database level: when a cart is given, only discounts whose `Discountable` entries (`condition` or `limitation`) match the cart's products or variants, or whose `collections()`/`brands()` pivot `type` is `condition` and matches a collection or brand on a cart line, are loaded at all. Second, each loaded discount's own `apply()` re-checks the full set of conditions (`checkDiscountConditions()`) and, for `PercentageOff`/`FixedAmountOff`, narrows to eligible lines via `TargetsCartLines` (`limitation`/`exclusion` on collections, brands, and `Discountable` entries).

Discounts are applied as one step in the cart calculation step list (`Lunar\Core\Enums\StepList::CartCalculation`), after lines and shipping are calculated and before tax:

```
CalculateLines → ApplyShipping → CalculateShippingSubTotal → ApplyDiscounts → CalculateTax → Calculate
```

`Lunar\Core\Pipelines\Cart\ApplyDiscounts` resets `$cart->discounts` and `$cart->discountBreakdown`, then calls `Discounts::apply($cart)`, which runs each eligible discount's type in turn. Each type mutates the affected `CartLine` totals (`discountTotal`, `subTotalDiscounted`) directly and, if it applied, records a `Lunar\Core\ValueObjects\Cart\DiscountBreakdown` describing what happened:

```php
Lunar\Core\ValueObjects\Cart\DiscountBreakdown
```

| Property | Type | Description |
|:---------|:-----|:------------|
| `price` | `PriceValue` | Total amount deducted by this discount |
| `lines` | `Collection<DiscountBreakdownLine>` | The affected cart lines and the quantity of each affected by this discount |
| `discount` | `Discount` | The discount that produced this breakdown |

```php
Lunar\Core\ValueObjects\Cart\DiscountBreakdownLine
```

| Property | Type | Description |
|:---------|:-----|:------------|
| `line` | `CartLine` | The affected cart line |
| `quantity` | `int` | How many units of that line the discount affected |

Because tax is calculated after discounts, discount amounts reduce the tax-relevant subtotal for the affected lines.

## Custom discount types

A custom discount type extends `Lunar\Core\DiscountTypes\AbstractDiscountType`:

```php
<?php

namespace App\DiscountTypes;

use Lunar\Core\DiscountTypes\AbstractDiscountType;
use Lunar\Core\Models\Cart;

class FreeShippingOverThreshold extends AbstractDiscountType
{
    public function getName(): string
    {
        return 'Free Shipping';
    }

    public function apply(Cart $cart): Cart
    {
        if (! $this->checkDiscountConditions($cart)) {
            return $cart;
        }

        // Custom discount logic...

        return $cart;
    }
}
```

This is a brief summary. See [Extending Discounts](/extending/discounts) for the full guide, including how to target cart lines, build a `DiscountBreakdown`, and register the type.
